# TagFlow 部署指南

本文档介绍如何通过 Docker / Docker Compose 部署 TagFlow。M9-1 起后端已通过 `rust-embed` 嵌入前端构建产物，单一可执行文件即可提供完整服务。

## 前置条件

- **Docker** 20.10+（建议 23+ 以默认启用 BuildKit）
- **Docker Compose** v2+（`docker compose` 子命令）
- 宿主机可用磁盘空间：≥ 2GB（镜像 + 数据 + 缩略图缓存）
- **NAS 用户特别注意**：SQLite 数据目录不可放在 NFS / SMB 共享卷上（详见 [卷规划](#卷规划)）

## 快速开始（3 步）

```bash
# 1. 克隆仓库
git clone https://github.com/sayeui/tagflow.git
cd tagflow

# 2. 准备环境变量（必填 JWT_SECRET 与 ADMIN_PASSWORD）
cp .env.example .env
${EDITOR:-vi} .env
#   TAGFLOW_JWT_SECRET：建议执行 `openssl rand -hex 32` 生成
#   TAGFLOW_ADMIN_PASSWORD：≥ 12 字节的强密码

# 3. 启动（首次会构建镜像，约 5-15 分钟取决于网络与 CPU）
mkdir -p ./cache ./library
chown -R 1000:1000 ./cache
docker compose up -d
```

启动后访问 `http://<host>:8080` 即可看到登录页面。首次登录用 `.env` 中设置的管理员账号；登录后请立即在「安全设置」修改密码。

查看启动日志确认健康：

```bash
docker compose logs -f tagflow
# 期望出现「API 服务器运行在 http://0.0.0.0:8080」
```

## 环境变量清单

| 变量 | 必填 | 默认 | 说明 |
|------|------|------|------|
| `TAGFLOW_JWT_SECRET` | ✅ | — | JWT 签名密钥（HS256），≥ 32 字节。更换会使所有已签发 token 失效，用户需重新登录 |
| `TAGFLOW_ADMIN_PASSWORD` | ✅ | — | 首次启动且 `users` 表为空时创建管理员用密码，≥ 12 字节。已有用户的部署不触发该校验 |
| `TAGFLOW_ADMIN_USERNAME` | ❌ | `admin` | 首次启动创建的管理员用户名 |
| `TAGFLOW_PORT` | ❌ | `8080` | API 监听端口 |
| `TAGFLOW_DB_PATH` | ❌ | `/app/data/tagflow.db`（镜像默认） | SQLite 数据库文件路径，Docker 中应保持绝对路径 |
| `TAGFLOW_CACHE_DIR` | ❌ | `/app/cache`（镜像默认） | 缩略图缓存目录 |
| `TAGFLOW_SCAN_INTERVAL` | ❌ | `3600` | 定时增量扫描间隔（秒）。后台 scheduler 启动后立即首轮扫描所有库，之后每 N 秒一轮，新增/删除文件下一轮自动同步。低于 60 的值会被 clamp 回 60；与手动 `POST /libraries/:id/scan` 共享 409 并发锁，同库不会并发扫描 |
| `TZ` | ❌ | `UTC` | 时区（影响日志时间戳与 time 标签生成） |

> **重要**：`TAGFLOW_JWT_SECRET` 与 `TAGFLOW_ADMIN_PASSWORD` 在生产部署中**必须**通过环境变量显式提供；缺失或长度不足将导致容器启动失败（release 构建强校验）。

## 卷规划

镜像内默认路径：

| 容器路径 | 内容 | 推荐挂载方式 | 说明 |
|---------|------|-------------|------|
| `/app/data` | SQLite 数据库（`tagflow.db` + `-wal` + `-shm`） | **named volume** | ⚠️ **不可**用 NFS / SMB 共享卷——SQLite WAL 模式要求 mmap 与文件锁，网络 FS 不可靠，可能导致数据损坏 |
| `/app/cache` | 缩略图缓存（`.webp` 文件） | bind mount | webp 是可重建的派生产物，损坏代价低；可放在 NAS |
| `/library/*` | 用户资源库（照片/视频，只读扫描源） | bind mount | 通过在前端添加 Local 类型 library 引用挂载点子目录 |

宿主目录权限：容器内运行用户 UID/GID = `1000:1000`，所有 bind mount 的宿主目录需提前 `chown`：

```bash
chown -R 1000:1000 ./cache ./library
```

## 常见运维操作

### 查看日志

```bash
docker compose logs -f tagflow          # 实时跟踪
docker compose logs --tail 200 tagflow  # 最近 200 行
```

### 重启

```bash
docker compose restart tagflow
```

### 升级

```bash
git pull
docker compose build           # 重新构建镜像
docker compose up -d           # 滚动重启
```

数据库迁移在容器启动时由 `sqlx::migrate!()` 自动执行，无需手动操作。

### 备份与恢复

**热备份**（推荐，无需停服）：

```bash
docker compose exec tagflow \
    wget -qO- http://127.0.0.1:8080/api/auth/login || true   # 健康检查
docker run --rm -v tagflow_tagflow_data:/data \
    alpine:3.20 sqlite3 /data/tagflow.db ".backup '/data/backup-$(date +%F).db'"
docker run --rm -v tagflow_tagflow_data:/data \
    alpine:3.20 cat "/data/backup-$(date +%F).db" > ./backup-$(date +%F).db
```

> ⚠️ 不要直接拷贝 `tagflow.db` 而忽略 `-wal` 与 `-shm`：未 checkpoint 的事务会丢失。SQLite 官方推荐用 `.backup` 命令做在线热备。

**恢复**：先停服，替换 `/app/data/tagflow.db`，再启服。

### 重置管理员密码

容器内提供 `reset-password` CLI 工具（与主程序共用 `infra::config::db_url()`）：

```bash
# 交互式输入新密码
docker compose exec tagflow reset-password --username admin

# 直接传参
docker compose exec tagflow reset-password \
    --username admin --new-password STRONG_NEW_PASSWORD_12
```

## 多架构镜像构建（amd64 + arm64）

默认 `docker build` 只构建 host 架构。如需为 ARM NAS（如 Synology DS423+、树莓派）构建：

```bash
# 一次性：安装 QEMU 模拟器
docker run --privileged --rm tonistiigi/binfmt --install all

# 创建 buildx builder
docker buildx create --use --name tagflow-builder

# 构建并加载到本地 docker（amd64 + arm64）
docker buildx build \
    --platform linux/amd64,linux/arm64 \
    -t tagflow:latest \
    --load .

# 或推送到镜像仓库（如 GHCR）
docker buildx build \
    --platform linux/amd64,linux/arm64 \
    -t ghcr.io/<user>/tagflow:latest \
    --push .
```

> **性能提示**：amd64 host 用 QEMU 模拟构建 arm64 预计 **20-60 分钟**（Rust release 全量编译）。后续 M9-3 将引入 `cross` 工具替代，本地原生速度交叉编译。

## 注意事项

### SQLite WAL 与网络文件系统

SQLite 官方明确警告：**WAL 模式不能工作在网络文件系统**（NFS、SMB/CIFS、部分 NAS 厂商的私有协议）。原因：

- WAL 用 mmap 共享内存做进程间协调
- 网络卷的文件锁语义不可靠
- 多个客户端并发访问同一 `tagflow.db` 会触发数据损坏

**建议**：`/app/data` 始终用 Docker named volume 或宿主机本地 ext4/btrfs 目录。NAS 用户场景：

- ✅ Synology DSM：用本机 Docker 卷（默认行为）
- ❌ Synology DSM + NFS 共享给其他设备访问同目录：避免
- ✅ 群晖 + 本机 Docker 跑 TagFlow + SMB 共享给客户端：data 用本机 Docker 卷，library 可 SMB

### 容器用户 UID 1000

镜像以非 root 用户 `tagflow` (UID/GID 1000) 运行。所有 bind mount 的宿主目录必须可被 UID 1000 读写。检查：

```bash
docker compose exec tagflow id
# 期望：uid=1000(tagflow) gid=1000(tagflow) groups=1000(tagflow)
```

如出现权限错误，在宿主机执行：

```bash
chown -R 1000:1000 ./cache ./library
```

### FFmpeg 可用性

容器内 FFmpeg 通过 `apk add ffmpeg` 安装在 `/usr/bin/ffmpeg`。验证：

```bash
docker compose exec tagflow ffmpeg -version
```

如需特定版本（如硬件加速），可在 Dockerfile runtime stage 替换为静态二进制。

### 防火墙

容器对外暴露端口由 `docker-compose.yml` 的 `ports: - "8080:8080"` 控制。生产部署建议：

- 反向代理（Caddy / Nginx）做 TLS 终止
- 仅在内网暴露，避免公网直连
- 配置 fail2ban 防暴力破解

## 故障排查

### 容器启动失败

```bash
docker compose logs tagflow | tail -50
```

常见原因：
- `TAGFLOW_JWT_SECRET` 长度 < 32 字节 → 重新生成密钥
- `TAGFLOW_ADMIN_PASSWORD` 长度 < 12 字节 → 用更强密码
- 卷权限错误 → `chown -R 1000:1000 ./cache`
- 端口被占用 → 修改 `docker-compose.yml` 的 `ports`

### 缩略图不生成

```bash
docker compose exec tagflow ffmpeg -version       # 验证 ffmpeg
docker compose exec tagflow ls -la /app/cache    # 检查 cache 目录可写
docker compose logs tagflow | grep worker        # 查看后台 worker 日志
```

### SPA 路由刷新返回 404

不应发生。M9-1 起后端 `static_handler` 已实现 SPA fallback；任何非 `/api/*` 路径未命中静态资源时返回 `index.html`。如出现请检查镜像是否为最新构建。

## 镜像构建详情

参见 [`Dockerfile`](../Dockerfile) 顶部注释。多阶段：

1. `node:20-alpine` 构建前端 → `/ui/dist`
2. `rust:1.92-alpine` + `cargo-chef` 分层缓存 + `cargo build --release` → `/tagflow-core`
3. `alpine:3.20` + ffmpeg + tini 运行时

镜像体积约 80-100MB（运行时层），首次构建约 5-15 分钟（含 cargo-chef cook 全量编依赖与 SQLite C 源码），后续命中缓存约 30 秒。
