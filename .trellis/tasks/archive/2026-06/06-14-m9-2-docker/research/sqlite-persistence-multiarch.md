## TL;DR（≤500 字总结）

**A. 持久化方案**
SQLite 官方明确说 **WAL 不能工作在网络文件系统**，因为 `wal-index` 用 mmap 共享内存做进程间协调，跨主机无法实现。NAS 上若仅本机 Docker（同一 Linux 内核）访问该路径，理论上能跑，但实际多数 NAS 用户会通过 SMB/NFS 把同一目录共享给其他设备，再加上 Docker bind mount，触发 SQLite 锁的 race 概率显著上升。**建议**：`/app/data`（含 `tagflow.db` + `-wal` + `-shm`）始终落在 **Docker named volume** 或宿主机本地 ext4/btrfs 目录，**不要**直接挂载 NAS 共享目录。缩略图 `cache/` 可放 bind mount（webp 是死文件，损坏代价低）。资源库（`/library`）本身就是只读扫描源，bind mount 无问题。

bind mount vs named volume：
- bind mount 优势：宿主机直接 `ls/backup`，NAS 用户最熟悉；缺点：UID/GID 与容器非 root 用户对齐麻烦。
- named volume 优势：Docker 托管、权限隔离清晰；缺点：宿主路径在 `/var/lib/docker/volumes/...`，备份必须走 `docker run --rm -v ... tar`。

**B. 多 arch 策略**
本项目依赖（argon2 纯 Rust、jsonwebtoken 用 hmac 纯 Rust、opendal `services-fs` 无 reqwest、sqlx-sqlite 0.8 仅 `libsqlite3-sys` bundled C 源码）**没有 ARM 不兼容的 C 依赖**。sqlx-sqlite 的 `bundled` feature 意味着每次构建都会重新编译 SQLite C 源（约几秒到几十秒，cc crate 自动跨架构）。

**三种构建路线**：
1. **buildx + QEMU 模拟**：最简单，单条命令出多 arch 镜像，但 Rust release 全量编译在 QEMU 下慢 5-20 倍，amd64 host 上构建 arm64 **预计 20-60 分钟**（取决于 CPU）。CI 上可接受，本地不爽。
2. **`cross` 工具**：本地一条命令交叉编译出 arm64 二进制，再嵌入 Dockerfile。Rust 全量编译保持原生速度（amd64 host 上构建 arm64 **预计 5-10 分钟**）。`aarch64-unknown-linux-musl` 是 cross 一级支持目标，可输出完全静态二进制，scratch 镜像运行。
3. **GitHub Actions 矩阵 + manifest 合并**：amd64 runner 出 amd64 镜像，arm64 runner（或 cross）出 arm64 镜像，最后 `docker buildx imagetools create -t xxx:latest xxx:amd64 xxx:arm64` 合并。**CI 复杂度最高但产物最优**。

**MVP 范围建议**：先做 amd64-only 的 buildx（甚至 `docker build`）出镜像，**defer 多 arch 到 M9-3**。Dockerfile 用 multi-stage 写好，预留 `--platform=$BUILDPLATFORM` 注释，后续切 cross / multi-node 改动很小。

## A. SQLite + Docker 持久化

### A.1 SQLite 官方对 WAL + 网络文件系统的明确警告

**[WAL doc §1 Overview](https://www.sqlite.org/wal.html)** 原文：

> All processes using a database must be on the same host computer; **WAL does not work over a network filesystem**. This is because WAL requires all processes to share a small amount of memory and processes on separate host machines obviously cannot share memory with each other.

**[WAL doc §7 Implementation Of Shared-Memory For The WAL-Index](https://www.sqlite.org/wal.html#_implementation_of_shared_memory_for_the_wal_index)**：

> The wal-index is implemented using an ordinary file that is **mmapped** for robustness. Early (pre-release) implementations of WAL mode stored the wal-index in volatile shared-memory, such as files created in `/dev/shm` on Linux... Using an ordinary disk file to provide shared memory has the disadvantage that it might actually do unnecessary disk I/O by writing the shared memory...

**[How To Corrupt](https://www.sqlite.org/howtocorrupt.html) §2.1 Filesystems with broken or missing lock implementations**：

> ...locks do not always behave as advertised. This is especially true of **network filesystems and NFS in particular**. If SQLite is used on a filesystem where the locking primitives contain bugs, and if two or more threads or processes try to access the same database at the same time, then **database corruption might result**.

**§1.2 Backup or restore while a transaction is active** 列出 4 种安全备份方法：
1. `sqlite3_rsync` 工具
2. CLI `.dump` 命令（纯 SQL 文本）
3. CLI `.backup FILE` 命令（在线热备份，使用 backup API）
4. C `sqlite3_backup_*` API

> It is also safe to make a copy of an SQLite database file as long as there are no transactions in progress while the copy is taking place. If the previous write transaction failed, then it is important that any rollback journal (the `*-journal` file) or write-ahead log (the `*-wal` file) be copied together with the database file itself.

### A.3 bind mount vs named volume（Docker 官方原文）

**[Engine storage / Volumes](https://docs.docker.com/engine/storage/volumes/)**（来源 `docker/docs/content/manuals/engine/storage/volumes.md`）：

> Volumes are the preferred mechanism for persisting data generated by and used by Docker containers. While bind mounts are dependent on the directory structure and OS of the host machine, volumes are completely managed by Docker. Volumes are a good choice for the following use cases:
> - Volumes are **easier to back up or migrate** than bind mounts.
> - You can manage volumes using Docker CLI commands or the Docker API.
> - Volumes can be more safely shared among multiple containers.
> - When your application requires **high-performance I/O**.

**[Engine storage / Bind mounts](https://docs.docker.com/engine/storage/bind-mounts/)**（来源 `docker/docs/content/manuals/engine/storage/bind-mounts.md`）：

> ### Considerations and constraints
> - Bind mounts have **write access to files on the host by default**.
> - Bind mounts are created to the Docker daemon host, not the client.
> - Containers with bind mounts are **strongly tied to the host**. Bind mounts rely on the host machine's filesystem having a specific directory structure available. This reliance means that containers with bind mounts may fail if run on a different host without the same directory structure.

**[Volumes - Back up, restore, or migrate data volumes](https://docs.docker.com/engine/storage/volumes/#back-up-restore-or-migrate-data-volumes)**：

```bash
# 备份 named volume（启动新容器挂载 volume + 主机目录做 tar）
$ docker run --rm --volumes-from dbstore -v $(pwd):/backup ubuntu \
    tar cvf /backup/backup.tar /dbdata
```

**NFS / CIFS 直接挂载**（volumes 文档同时给出，不推荐 SQLite 用）：

```bash
# NFSv4
$ docker service create --mount 'type=volume,source=nfsvolume,target=/app,\
volume-driver=local,volume-opt=type=nfs,volume-opt=device=:/var/docker-nfs,\
"volume-opt=o=addr=10.0.0.10,rw,nfsvers=4,async"' nginx:latest
```

### A.4 SQLite 备份建议（官方推荐方法对比）

| 方式 | 命令 | 适用场景 | 优势 | 劣势 |
|---|---|---|---|---|
| **`.backup` CLI** | `sqlite3 tagflow.db ".backup '/backup/backup.db'"` | 在线热备 | 不需要停服务；自动用 backup API 处理并发；只产生单文件 | 需要 sqlite3 CLI 在容器内 |
| **`.dump`** | `sqlite3 tagflow.db ".dump" > backup.sql` | 在线热备 | 文本可读、版本兼容性好 | 恢复慢；schema 重新解析 |
| **停机复制 3 文件** | `cp tagflow.db tagflow.db-wal tagflow.db-shm` | 离线 | 最快 | 必须确保无活跃连接（`docker compose stop`） |
| **直接拷 `.db`** | ❌ | —— | —— | **会丢未 checkpoint 的事务**；不要做 |

**SQLite CLI `.backup` 用法来源**：`https://www.sqlite.org/cli.html` — `> .backup ?DB? FILE  Backup DB (default "main") to FILE`，等同调用 C `sqlite3_backup_*` API。

### A.5 容器非 root 用户与卷权限

**[userns-remap doc](https://docs.docker.com/engine/security/userns-remap/)**（来源 `docker/docs/content/manuals/engine/security/userns-remap.md`）：

> The best way to prevent privilege-escalation attacks from within a container is to configure your container's applications to run as **unprivileged users**. For containers whose processes must run as the root user within the container, you can re-map this user to a less-privileged user on the Docker host.

> This re-mapping is transparent to the container, but **introduces some configuration complexity in situations where the container needs access to resources on the Docker host, such as bind mounts** into areas of the filesystem that the system user cannot write to. From a security standpoint, it is best to avoid these situations.

**[Prerequisites §3](https://docs.docker.com/engine/security/userns-remap/#prerequisites)**：

> If there are any locations on the Docker host where the unprivileged user needs to write, adjust the permissions of those locations accordingly.

#### 实际可工作模式

| 方案 | 实现方式 | 适合项目 |
|---|---|---|
| **A. 镜像内非 root + bind mount 前提 chown** | Dockerfile `RUN useradd -u 1000 tagflow && USER tagflow`；compose 卷加 `user: "1000:1000"`；用户首次部署 `chown -R 1000:1000 ./data ./cache` | 推荐 MVP 用 |
| **B. named volume + 入口脚本 chown** | 容器启动 `entrypoint.sh` 检查卷 owner，第一次以 root 启动改权限再降权 | 增加复杂度 |
| **C. docker userns-remap** | 守护进程级配置，所有容器 UID 重映射 | 用户改宿主 docker 配置，部署文档负担大 |
| **D. rootless docker** | docker daemon 以普通用户运行 | 用户需切换整套 docker 安装 |

**推荐 A**：MVP 不强求 entrypoint chown，部署文档写明 `chown 1000:1000` 一步即可，与 `tagflow-core` 现有 `infra::config` 透明路径设计一致。

## B. Rust multi-arch 镜像

### B.1 Docker buildx 三种策略（官方原文）

**[Multi-platform builds](https://docs.docker.com/build/building/multi-platform/)**（来源 `docker/docs/content/manuals/build/building/multi-platform.md`）：

> ### Strategies
> You can build multi-platform images using three different strategies, depending on your use case:
> 1. **Using emulation, via QEMU**
> 2. **Use a builder with multiple native nodes**
> 3. **Use cross-compilation with multi-stage builds**

#### QEMU

> Building multi-platform images under emulation with QEMU is the **easiest way** to get started if your builder already supports it. Using emulation requires no changes to your Dockerfile...
> **Emulation with QEMU can be much slower than native builds, especially for compute-heavy tasks like compilation and compression or decompression.** Use multiple native nodes or cross-compilation instead, if possible.

> Official BuildKit releases bundle QEMU user-mode emulators, so in most cases you don't need to install QEMU manually.

安装 QEMU（一次）：

```bash
$ docker run --privileged --rm tonistiigi/binfmt --install all
```

#### Multiple native nodes

> Using multiple native nodes provide **better support for more complicated cases that QEMU can't handle**, and also provides better performance. You can add additional nodes to a builder using the `--append` flag.

```bash
$ docker buildx create --use --name mybuild node-amd64 mybuild
$ docker buildx create --append --name mybuild node-arm64
$ docker buildx build --platform linux/amd64,linux/arm64 .
```

#### Cross-compilation

> Depending on your project, if the programming language you use has good support for cross-compilation, you can leverage multi-stage builds to build binaries for target platforms from the native architecture of the builder. Special build arguments, such as `BUILDPLATFORM` and `TARGETPLATFORM`, are automatically available.

> Tip You may also want to consider checking out **[xx - Dockerfile cross-compilation helpers](https://github.com/tonistiigi/xx)**. xx is a Docker image containing utility scripts that make cross-compiling with Docker builds easier.

Go 示例（Rust 类似思路）：

```dockerfile
# syntax=docker/dockerfile:1
FROM --platform=$BUILDPLATFORM golang:alpine AS build
ARG TARGETOS
ARG TARGETARCH
WORKDIR /app
RUN GOOS=${TARGETOS} GOARCH=${TARGETARCH} go build -o server .
FROM alpine
COPY --from=build /app/server /server
ENTRYPOINT ["/server"]
```

### B.3 GitHub Actions 多 arch 流水线

社区主流模式（Docker buildx doc 提及）：

```yaml
jobs:
  build:
    strategy:
      matrix:
        include:
          - { arch: amd64, runner: ubuntu-latest }
          - { arch: arm64, runner: ubuntu-24.04-arm }  # GitHub 原生 arm64 runner
    steps:
      - uses: docker/build-push-action@v5
        with:
          platforms: linux/${{ matrix.arch }}
          tags: ghcr.io/org/tagflow:latest-${{ matrix.arch }}
          push: true

  manifest:
    needs: build
    steps:
      - run: |
          docker buildx imagetools create -t ghcr.io/org/tagflow:latest \
            ghcr.io/org/tagflow:latest-amd64 \
            ghcr.io/org/tagflow:latest-arm64
```

### B.5 sqlx-sqlite 0.8 `Cargo.toml` 关键片段（影响 cross 行为）

```toml
[dependencies.libsqlite3-sys]
version = "0.28.0"
default-features = false
features = [
    "pkg-config",
    "vcpkg",
    "bundled",         # 关键：源码编译
    "unlock_notify"
]
```

> `bundled` 意味着 SQLite C 源码与 sqlx 一起编译，**不依赖宿主/镜像系统 libsqlite3**。运行时镜像可以是 alpine/scratch/debian-slim 任一种，无需 `apk add sqlite-libs`。

### B.6 opendal 0.50 Cargo.toml 关键片段

```toml
[features]
default = ["reqwest/rustls-tls", "executors-tokio", "services-memory"]
services-fs = ["tokio/fs", "internal-tokio-rt"]
```

> 项目 `Cargo.toml` 写的是 `opendal = { version = "0.50", features = ["services-fs"] }`，**没启用 default-features**（实际需查 lock 文件确认；若启用 default 仍会拉 reqwest+rustls，rustls 是纯 Rust，仍兼容 ARM）。无 openssl-sys。

## Recommendations（针对本项目）

### A. 持久化方案（M9-2 MVP）

1. **`/app/data` → Docker named volume `tagflow_data`**
   - 包含 `tagflow.db` + `tagflow.db-wal` + `tagflow.db-shm` 三个文件
   - 默认 driver `local`，宿主路径 `/var/lib/docker/volumes/tagflow_data/_data`
   - **绝不**让用户挂载到 NAS SMB/NFS 共享目录（部署文档显式警告）
2. **`/app/cache` → bind mount `./cache`**（可放 NAS）
   - webp 是无状态产物，可重建；损坏代价低
   - NAS 用户可定期清理/迁移
3. **`/library` → bind mount 用户照片库**（只读扫描源）
   - 已经是用户主要资源目录，bind mount 是唯一合理选项
4. **compose 文档示例同时给 named volume 与 bind mount 两种 data 写法**，让用户选
5. **非 root UID 1000**：Dockerfile `useradd -u 1000 -M tagflow`，部署文档要求 `chown -R 1000:1000 ./cache`（library 只读不需改）；**不用 userns-remap/rootless**，复杂度过高
6. **备份命令写进部署文档**：
   ```bash
   docker compose exec tagflow sqlite3 /app/data/tagflow.db ".backup '/app/data/backup-$(date +%F).db'"
   ```

### B. multi-arch 策略（M9-2 vs M9-3）

#### **M9-2 MVP（强烈建议）**：
- **只做 amd64**：`docker build -t tagflow:latest .` 一条命令
- Dockerfile 写成多阶段 + `AS` 别名，运行时基础镜像用 `debian:bookworm-slim`（不是 alpine）
- **理由**：
  1. sqlx-sqlite `bundled` + `cc` 在 alpine musl 下偶尔有 build script 报错（需 `apk add musl-dev`）；glibc 镜像零额外配置
  2. FFmpeg `debian:bookworm-slim` 用 `apt-get install ffmpeg` 一行解决；alpine `apk add ffmpeg` 包版本旧且部分 NAS 厂商自家 alpine 不带 ffmpeg
  3. 镜像体积 alpine 约 80-100MB，debian-slim 约 120-160MB，差距不值得为兼容性冒险
- **预留多 arch 切换点**：Dockerfile 加注释说明 `# 多 arch 时改这里`，第二阶段构建基础 `FROM --platform=$TARGETPLATFORM debian:bookworm-slim`

#### **defer 到 M9-3（CI/CD 任务）**：
- 用 `cross` 在 GitHub Actions 上同时构建 amd64 + arm64 静态 musl 二进制
- 用 buildx manifest 合并两个 tag 推 GHCR
- 运行时基础镜像可同时切回 alpine（此时已验证 cross + alpine 兼容）
- 推出 arm64 镜像前的 PRD 必要性：用户调研是否有真实 ARM NAS 用户（Synology DS423+ 是 ARM；群晖主流仍是 x86）
